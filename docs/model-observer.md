# 호출 모델 일치성 검증

세션 탐색의 모델 호출 표는 **모델 호출 시각 / 호출 모델 / 응답 모델 / 강도 / 모델 일치성** 순서입니다.
호출 모델은 전송 메시지, 응답 모델은 서버 응답에서 가져옵니다. 강도는 로컬 기록의 설정값입니다.
프록시 관측이 없으면 호출 모델에 기존 모델명과 `· 설정`을 표시하고 응답 모델은 `미관측`으로 표시합니다.
설정값을 실제 전송 관측으로 간주하지 않으며 일치성은 `확인 불가`로 남습니다.
세션 요약과 선택 구간 요약에 검증 건수/전체 호출 건수, 일치·불일치·확인 불가를 표시합니다.

## 일반 사용자: 배포판에서 켜기

Python 설치나 별도 터미널이 필요 없습니다.

1. `Codexon-Setup.exe`로 설치한 뒤 시작 메뉴에서 **Codexon**을 실행합니다.
2. **설정 → 프록시 → 프록시 사용**을 켭니다. 독립 프로세스 준비, 짧은 모델 검증 호출 1회, 연결 적용과 로그인 자동 시작 등록을 한 번에 처리합니다. 준비·검증 중에는 전역 Codex 연결을 변경하지 않습니다.
3. 성공 후 **Codex 앱을 직접 완전히 종료한 뒤 다시 실행**합니다. 기존 Codex 프로세스는 이전 설정을 유지할 수 있습니다. Codexon은 Codex를 자동 종료하지 않습니다.
4. 끄면 직접 연결 설정을 복원하고 로그인 자동 시작을 해제합니다. 진행 중인 응답은 끝까지 전달하고 연결 종료를 기다립니다. 이후 Codex를 재시작하면 직접 연결 설정이 적용됩니다.

켜는 도중 다시 끄면 검증을 취소하고 적용한 설정을 되돌립니다. 실패 시 상태와 원인을 표시하며 자동으로 재시작을 반복하지 않습니다. 사용자가 바꾼 서버 주소나 다른 프로그램 소유의 작업은 덮어쓰지 않습니다.

GUI 로그인 자동 시작은 **설정 → 일반**에서 따로 선택합니다. 프록시의 자동 시작과 예약 복구 점검은 프록시 스위치에 연동됩니다. 프록시는 GUI와 독립적으로 실행되며, GUI를 종료해도 중계는 유지됩니다.

예약 점검은 반복 확인된 로컬 장애를 알리며 연결 설정을 자동 변경하거나 모델 요청을 보내지 않습니다. 연결 복구가 필요하면 **시작 메뉴 → Codexon 연결 복구 → 직접 연결로 복원**을 사용합니다. 복원 성공 후 진행 중인 작업을 마치고 Codex를 다시 시작하세요. 설정 복원과 실제 모델 통신 성공은 구분합니다. 자세한 절차는 [사용 안내](user-guide.ko.md)에 있습니다.

**설정 → 정보·문제 해결 → 업데이트 확인 및 설치**에서 앱과 프록시를 함께 업데이트합니다. 기존 연결이 끝난 뒤 프록시를 교체하며, 요청을 강제 종료하거나 재전송하지 않습니다. 새 프록시 실행에 실패하면 이전 프록시로 복원합니다. 이전 버전의 프록시는 안전한 전환이 끝날 때까지 기존 감시기를 유지하므로 사용 중인 폴더를 삭제하지 마세요.

설정 백업·복원 정보·모델 관측 원장은 `%USERPROFILE%\.cachemonitor\model-observer`에 저장합니다.
MSIX의 LocalAppData 리다이렉트와 무관하게 Codex 내부 실행과 일반 Windows 실행이 같은 파일을 사용합니다.
다른 설정·대화 원본·사용량 기록은 수정하지 않습니다. 기존 사용자 지정 공급자나 임의의
서버 주소는 자동으로 덮어쓰지 않습니다. 자동 연결은 첫 번째 Codex 홈을 대상으로 합니다.

## 개발 실행

저장소 폴더의 PowerShell에서 최초 한 번 설치합니다.

```powershell
python -m pip install -r requirements-proxy.txt
```

프록시를 실행한 터미널을 유지합니다. ChatGPT 로그인 경로가 기본입니다.

```powershell
python -m cachemonitor.model_proxy
```

다른 터미널에서 이 실행에만 프록시 경로를 지정하고 Codex를 사용합니다.

```powershell
codex -c 'openai_base_url="http://127.0.0.1:8768"'
```

CacheMonitor의 새 소스를 실행합니다. 기존 설치 앱이 실행 중이면 트레이의 종료 메뉴로 닫은 후 실행합니다.

```powershell
python run.py
```

위 개발용 단독 프록시 명령은 사용자 `config.toml`, 시스템 프록시, 인증서, 자동 시작 설정을 변경하지 않습니다.
프록시 종료 후에는 위 URL 재지정 없이 Codex를 실행하면 원래 경로를 사용합니다.

데스크톱 앱 전체 적용은 배포판의 프록시 스위치를 사용하세요. 원장 상태와 어긋나는 수동 URL 설정을 피할 수 있습니다.

API 키 인증을 사용하는 별도 환경에서는 `--upstream openai`를 지정합니다.
기존 ChatGPT 로그인 실행에 이 옵션을 사용하지 않습니다.

## 기록과 판정

- 기본 파일: `%USERPROFILE%\.cachemonitor\model-observer\model-evidence.sqlite`.
- 별도 색인을 쓰는 경우 `--evidence-path`를 해당 색인과 같은 폴더의 `model-evidence.sqlite`로 지정합니다.
- 다른 Codex 홈을 관찰할 때는 프록시와 Codexon 모두 같은 `--codex-home`을 사용합니다.
- Codex 홈과 정확한 응답 ID가 일치하는 사용량 기록에만 연결합니다. 시각이나 연결 순서로 세션을 추정하지 않습니다.
- 요청·응답 모델 문자열이 같으면 `일치`, 다르면 `불일치`입니다. 별칭이나 스냅샷 이름은 자동으로 합치지 않습니다.
- 관측 누락, 요청·응답 연결 실패, 관측 충돌은 `확인 불가`입니다. 과거 미관측 호출은 소급 추정하지 않습니다.
- 서버 응답에 명시된 모델명을 비교하며, 서버 내부 실행 모델을 독립적으로 증명하지 않습니다.
- 기존 토큰·비용 계산의 모델 기준은 유지합니다. 비용을 응답 모델 기준으로 자동 재계산하지 않습니다.
- 실패·연결 중단 및 사용량이 없는 워밍업 관측도 별도 원장에 남습니다. 사용량에 연결되지 않은 관측을 호출 수에 합산하지 않습니다.
- 인증 헤더·대화·도구·응답 본문은 중계에만 사용하며 저장하지 않습니다. 저장 필드는 모델명·식별자·시각·상태뿐입니다.

## 진단과 검증

`http://127.0.0.1:8768/health`에서 프록시의 요청·응답·저장 오류·중계 오류 건수를 확인합니다.
저장 실패는 중계를 재시도하지 않으며, 누락된 관측은 확인 불가로 남습니다.
운영 프록시는 최대 1,024개 관측 사본을 제한 큐로 넘기고 전용 저장 스레드가 SQLite 연결을 소유합니다.
큐 포화·저장 실패는 관측 누락으로 기록하며 완료된 레코드도 누락 구간과 겹치면 확정 모델 판정에서 제외합니다.
`storage_pending`, `observation_dropped`, `observation_gap_pending`으로 저장 지연·누락을 구분합니다.
정상 종료 시 잔여 저장을 기다리며 완료되지 않으면 종료 오류로 알립니다. 본문 해석과 네트워크 비용은 여전히 남습니다.
호출 상세의 지연은 요청 메타데이터 관측부터 `response.in_progress` 생성 신호 또는 완료 수신까지의
동일 프로세스 단조시간 차이입니다. HTTP 요청은 업로드 메타데이터 해석 완료가 시작점입니다.
별도의 실제 기록 시각도 보존하며 과거 레코드의 `ts` 차이로 지연을 계산하지 않습니다.
정확한 응답 ID로 연결된 완료 호출만 제공하고, 생성 신호를 첫 출력·생각 시간·완료 예상으로 해석하지 않습니다.
요청에 명시된 `prompt_cache_retention`은 비교 구간 식별에만 사용합니다. 없는 정책이나 모델별 최소 캐시
길이·실제 보존 시간은 추정하지 않습니다.
프록시는 `127.0.0.1`에만 바인딩하고 상위 목적지를 고정하며 브라우저 Origin 요청을 거부합니다.
`openai_base_url`은 모델 호출뿐 아니라 이미지 생성·편집과 다른 도구 요청에도 사용됩니다.
프록시는 개별 API 경로·메서드를 허용 목록으로 제한하지 않고 설정된 상위 base URL 아래로 중계합니다.
인코딩된 경로·쿼리, 중복 헤더, 압축 본문과 서버 상태 코드를 보존하며 리다이렉트를 대신 따라가거나
다른 요청의 쿠키를 재사용하지 않습니다. 이미지·파일 업로드는 전체 내용을 메모리에 모으지 않고 스트리밍합니다.
모델 관측은 `/responses`에만 적용합니다. 이미지·도구 호출은 모델 관측 원장에 추가하지 않습니다.
`/health`의 `forwarded_http_requests`와 `forwarded_http_responses`는 도구를 포함한 HTTP 중계 건수이며,
기존 `requests`·`responses`는 모델 관측 건수입니다. `/health`는 로컬 진단용으로 예약된 경로입니다.
WebSocket과 HTTP/SSE를 모두 지원합니다. SSE 조각 경계, 동시 stream_id, 중복 응답, 응답 중 모델명 변경을 처리합니다.
지원하지 않는 압축 본문·너무 큰 관측 이벤트는 내용을 바꾸지 않고 전달하며 모델 확인이 불가능할 수 있습니다.

2026.09.19.2부터 gzip/deflate/zstd 요청·응답의 관측용 사본을 해석하며, SSE는 Content-Type이 없거나
application/octet-stream이어도 본문 형식으로 식별합니다. HTTP 중계는 HTTPS에서 HTTP/2를 협상하고,
서버가 지원하지 않으면 HTTP/1.1을 사용합니다. WebSocket은 그대로 유지하며 중계기가 요청을 자동 재전송하지 않습니다.
취소 시 해당 상류 연결을 닫습니다. 다른 요청의 연결을 함께 닫지 않도록 동시에 처리하는 HTTP 요청은
각각 연결을 임대하고, 완료한 연결은 재사용합니다. 최대 동시 HTTP 요청은 100개입니다.
Windows 프록시 프로세스는 Selector 이벤트 루프를 사용하므로 운영체제의 512 소켓 제한을 받습니다.
모델 관측은 디코딩된 128MiB까지이며 HTTP 업로드 자체는 이 크기로 제한하지 않습니다.

Fast/Standard는 실제 요청의 service_tier를 우선 사용합니다. 과거 호출은 해당 턴에 앞서 적용된
thread_settings_applied 스냅샷과 명시적 턴 설정을 사용하며, 현재 설정을 과거 호출에 소급하지 않습니다.
응답의 service_tier는 별도 보존하므로 요청 등급과 혼동하지 않습니다. 근거가 없는 과거 호출은 미확인으로 남습니다.
첫 실행 때 기존 앱 색인에서 빠진 설정 스냅샷을 한 번 다시 읽으므로 일시적으로 기록 정리 시간이 필요합니다.

`/health`의 active_relays/recent_relays는 최근 최대 32개 연결의 종료 방향·코드·송수신 시각·바이트 수를
메모리에만 보관합니다. 요청 본문·인증 헤더·응답 내용은 포함하지 않으며 프로세스 재시작 시 사라집니다.
client_disconnects는 클라이언트 취소/연결 종료, relay_errors는 중계 오류, observation_skips는
압축 형식이나 관측 한도 때문에 메타데이터를 읽지 못한 경우입니다.

```powershell
python -m pytest -q
python tools/probe_model_proxy.py --codex-exe 'C:\path\to\codex.exe'
```

두 번째 명령은 실제 로그인으로 짧은 시험 호출을 수행하므로 사용량이 발생합니다.
시험은 임시 프록시 포트와 임시 관측 원장을 사용하고, `--ephemeral` 및 실행 인자 재지정으로
영구 설정을 바꾸지 않습니다. 민감 내용을 제외한 결과는 `artifacts/model-proxy-live.json`에 저장합니다.

## 프록시 업데이트

설정 → 프록시에서 버전이 다르면 **프록시 업데이트**를 누릅니다. 업데이트는 Windows 작업 스케줄러에서 독립적으로 진행되어 앱을 닫아도 유지됩니다. 기존 연결이 모두 종료될 때까지 기다리므로 작업을 마친 뒤 Codex를 닫으면 적용됩니다. 대기 중에는 같은 버튼으로 예약을 취소할 수 있습니다. 24시간 동안 연결이 유지되면 예약만 종료하며 기존 프록시는 유지합니다.

새 실행 파일의 Qt 런타임을 먼저 검사하고 기존 요청이 끝난 뒤 같은 주소로 교체합니다. 전환 중 들어온 요청도 기존 drain 프로토콜로 마무리하며 요청을 재전송하지 않습니다. 새 버전의 서비스 식별·버전·상태와 독립 감시를 확인하지 못하면 이전 실행 파일로 복구합니다. 업데이트 상태와 복구 정보는 로컬에 저장하며 작업 프로세스가 비정상 종료되면 스케줄러가 재시도합니다. 전환 중에는 설정 변경을 잠급니다.

프록시 주소와 Codex 설정을 바꾸지 않습니다. 교체 시점에 새 연결을 시도하면 잠깐 연결이 실패할 수 있으므로, 완료 후 Codex를 다시 여는 것이 가장 확실합니다. 이전 배포 폴더는 실행 중인 프록시와 복구에 필요하므로 업데이트 완료 전 삭제하지 마세요.
